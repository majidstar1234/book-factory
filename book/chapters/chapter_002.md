# معماری گیت‌هاب اکشنز در اتوماسیون

## مقدمه

در فصل گذشته دیدیم که چگونه توسعه سیستم‌های مدرن و پردازش مدل‌های سنگین هوش مصنوعی، نیاز به زیرساخت‌های توزیع‌شده و مقیاس‌پذیر را اجتناب‌ناپذیر کرده است. اما مدیریت، تست، ساخت و استقرار نرم‌افزارها و مدل‌های هوش مصنوعی روی این زیرساخت‌های توزیع‌شده، بدون استفاده از ابزارهای «اتوماسیون» (Automation) خودکار، بسیار کند، پرخطا و هزینه‌بر خواهد بود.

با پیچیده‌تر شدن چرخه‌های توسعه نرم‌افزار و پیدایش مفاهیمی مانند «یکپارچه‌سازی مداوم» (Continuous Integration - CI) و «تحویل/استقرار مداوم» (Continuous Delivery/Deployment - CD)، ابزارهای مدیریت کد منبع دیگر فقط محل نگهداری فایل‌ها نیستند؛ بلکه به مرکز فرماندهی و اجرای خودکار فرآیندها تبدیل شده‌اند. در این میان، «گیت‌هاب اکشنز» (GitHub Actions) به عنوان یک پلتفرم رویدادمحور (Event-driven) و توزیع‌شده برای اتوماسیون، به توسعه‌دهندگان اجازه می‌دهد تمامی مراحل چرخه حیات نرم‌افزار را در کنار مخزن کد مدیریت کنند.

در این فصل، معماری داخلی گیت‌هاب اکشنز، اجزای تشکیل‌دهنده، نحوه مدیریت اجراکننده‌ها (Runners)، ساختارهای امنیتی و الگوهای پیشرفته اتوماسیون در پروژه‌های پیچیده نرم‌افزاری و هوش مصنوعی بررسی می‌شود.

## ۱. مفاهیم پایه و اجزای کلیدی گیت‌هاب اکشنز

برای درک نحوه عملکرد گیت‌هاب اکشنز، ابتدا باید با اجزای بنیادی تشکیل‌دهنده آن و رابطه میان آن‌ها آشنا شویم. گیت‌هاب اکشنز بر پایه یک ساختار هرمی از اجزا طراحی شده است که در ادامه به تشریح هر یک می‌پردازیم.

### فرآیند کاری (Workflow)
«فرآیند کاری» یک فرآیند خودکار پیکربندی‌پذیر است که یک یا چند «شغل» را اجرا می‌کند. این فرآیندها با استفاده از فایل‌های YAML تعریف می‌شوند و در مسیر `.github/workflows` در مخزن کد (Repository) قرار می‌گیرند. یک مخزن می‌تواند چندین فرآیند کاری داشته باشد؛ برای مثال، یک فرآیند برای تست کدها در هر درخواست کشیدن (Pull Request)، یک فرآیند برای آموزش روزانه مدل هوش مصنوعی و فرآیندی دیگر برای استقرار برنامه‌کاربردی در محیط عملیاتی.

### رویداد (Event)
«رویداد» یک فعالیت مشخص در مخزن است که باعث تحریک و شروع اجرای یک فرآیند کاری می‌شود. این رویدادها می‌توانند منشأ داخلی (مانند ارسال کد یا `push`، ایجاد درخواست کشیدن یا `pull_request` و ثبت یک گزارش خطا یا `issue`) یا منشأ خارجی (مانند فراخوانی از طریق Webhook، رویدادهای زمان‌بندی‌شده یا `cron job` و یا تحریک دستی یا `workflow_dispatch`) داشته باشند.

### شغل (Job)
یک فرآیند کاری از یک یا چند «شغل» تشکیل شده است. هر شغل مجموعه‌ای از «گام‌ها» است که روی یک «اجراکننده» مشخص اجرا می‌شود. به‌طور پیش‌فرض، شغل‌های موجود در یک فرآیند کاری به صورت موازی (Parallel) اجرا می‌شوند، اما می‌توان با تعریف وابستگی (Dependency)، اجرای آن‌ها را ترتیبی (Sequential) کرد.

### گام (Step)
«گام» کوچک‌ترین واحد اجرایی در یک شغل است. گام‌ها می‌توانند یک دستور شل (Shell Command) مانند اجرای یک اسکریپت پایتون باشند یا یک «اکشن» آماده را فراخوانی کنند. تمام گام‌های درون یک شغل، روی یک اجراکننده واحد و در یک محیط ایزوله اجرا می‌شوند و می‌توانند داده‌ها را از طریق سیستم‌فایل محلی با یکدیگر به اشتراک بگذارند.

### اکشن (Action)
«اکشن» یک برنامه مستقل و قابل بازاستفاده در گیت‌هاب اکشنز است که کارهای تکراری و پیچیده را ساده می‌کند. اکشن‌ها می‌توانند توسط خود گیت‌هاب، جامعه کاربری (Community) یا به صورت خصوصی توسط خود سازمان نوشته شوند. اکشن‌ها گام‌های ساختاریافته‌ای هستند که در بازارچه گیت‌هاب (GitHub Marketplace) به اشتراک گذاشته می‌شوند.

### اجراکننده (Runner)
«اجراکننده» سروری است که برنامه کاربردی گیت‌هاب اکشنز روی آن نصب شده و وظیفه گوش دادن به درخواست‌ها، اجرای شغل‌ها و ارسال گزارش وضعیت به سرور اصلی گیت‌هاب را بر عهده دارد. اجراکننده‌ها به دو دسته کلی تقسیم می‌شوند:
1. **اجراکننده‌های میزبان گیت‌هاب (GitHub-hosted Runners):** ماشین‌های مجازی مدیریت‌شده توسط گیت‌هاب (بر پایه لینوکس، ویندوز یا مک‌او‌اس) که برای هر اجرا به صورت موقت (Ephemeral) ساخته شده و پس از پایان کار کاملاً نابود می‌شوند.
2. **اجراکننده‌های خود-میزبان (Self-hosted Runners):** سرورهای فیزیکی، ماشین‌های مجازی یا کانتینرهایی که توسط خود سازمان تامین و مدیریت می‌شوند. این نوع اجراکننده‌ها برای کارهای سنگین (مانند آموزش مدل‌های هوش مصنوعی نیازمند کارت گرافیک GPU) یا دسترسی به شبکه‌های داخلی بسیار پرکاربرد هستند.

```
+-----------------------------------------------------------------+
|                       Workflow (فایل YAML)                      |
|                                                                 |
|  [Event: push/schedule]                                         |
|                                                                 |
|  +---------------------------+     +--------------------------+ |
|  |       Job A (Parallel)    |     |      Job B (Parallel)    | |
|  |  (Runs on: Ubuntu Runner) |     |  (Runs on: Self-hosted)  | |
|  |                           |     |                          | |
|  |  - Step 1: Checkout Code  |     |  - Step 1: Load GPU      | |
|  |  - Step 2: Run Unit Tests |     |  - Step 2: Train Model   | |
|  |  - Step 3: Run Action X   |     |                          | |
|  +---------------------------+     +--------------------------+ |
+-----------------------------------------------------------------+
```

## ۲. معماری و جریان کاری در گیت‌هاب اکشنز

معماری گیت‌هاب اکشنز بر پایه یک مدل توزیع‌شده، لایه متمرکز کنترل (Control Plane) و اجراکننده‌های غیرمتمرکز (Execution Plane) بنا شده است. این ساختار تضمین می‌کند که پلتفرم قابلیت مقیاس‌پذیری بالا، تحمل خطا و امنیت ایزوله‌شده داشته باشد.

### ۱. معماری لایه کنترل و ارکستراسیون
هنگامی که رویدادی در گیت‌هاب رخ می‌دهد، لایه کنترل گیت‌هاب اکشنز مراحل زیر را طی می‌کند:

1. **دریافت رویداد و ارزیابی شرط‌ها:** سیستم رویدادهای گیت‌هاب (Event Bus) رویداد رخ‌داده را تحلیل کرده و فایل‌های YAML مربوطه را در مسیر `.github/workflows` بررسی می‌کند.
2. **تولید نمودار جهت‌دار بدون چرخه (DAG):** گیت‌هاب براساس دستورات `needs` در تعریف شغل‌ها، یک «نمودار جهت‌دار بدون چرخه» (Directed Acyclic Graph - DAG) می‌سازد تا ترتیب اجرای شغل‌ها و وابستگی‌های موازی را مشخص کند.
3. **صف‌بندی شغل‌ها (Job Queueing):** شغل‌های آماده برای اجرا به یک صف مرکزی منتقل می‌شوند.
4. **تخصیص به اجراکننده (Runner Assignment):** اجراکننده‌های منتظر، از طریق مکانیزم کشش (Long Polling over HTTPS) وجود شغل جدید را بررسی کرده و با تطبیق برچسب‌ها (Labels) مانند `ubuntu-latest` یا `self-hosted`، شغل را دریافت می‌کنند.

```
[GitHub Event] ──> [Orchestrator / DAG Builder] ──> [Job Queue]
                                                         │
                                    ┌────────────────────┴────────────────────┐
                                    ▼                                         ▼
                        [GitHub-hosted Runner]                     [Self-hosted GPU Runner]
```

### ۲. اجرای ماتریسی (Matrix Strategy)
یکی از قابلیت‌های کلیدی گیت‌هاب اکشنز برای پردازش موازی، «استراتژی ماتریسی» (Matrix Strategy) است. این قابلیت به توسعه‌دهنده اجازه می‌دهد تا یک شغل واحد را روی ترکیبی از متغیرهای مختلف (مانند نسخه‌های مختلف پایتون، سیستم‌عامل‌های مختلف یا نسخه‌های کتابخانه‌ها) به صورت موازی اجرا کند. 

برای مثال، اگر بخواهید یک کتابخانه یادگیری ماشین را روی ۳ نسخه پایتون (۳.۹، ۳.۱۰، ۳.۱۱) و ۲ سیستم‌عامل (لینوکس و ویندوز) تست کنید، به جای نوشتن ۶ شغل جداگانه، یک شغل با ماتریس ۶‌تایی تعریف می‌کنید. ارکستراتور گیت‌هاب به صورت خودکار ۶ شغل مجزا ایجاد کرده و به اجراکننده‌ها تحویل می‌دهد.

### ۳. ذخیره‌سازی موقت و مدیریت آرتیفکت‌ها (Caching & Artifacts)
در فرآیندهای CI/CD، زمان ساخت و دانلود وابستگی‌ها (Dependencies) معمولاً بخش عمده‌ای از زمان اجرا را تشکیل می‌دهد. گیت‌هاب اکشنز دو مکانیزم اصلی برای مدیریت داده‌های بین اجراها و بین شغل‌ها ارائه می‌دهد:

* **کش (Caching):** استفاده از اکشن `actions/cache` برای ذخیره‌سازی فایلهای وابستگی (مانند پکیج‌های `pip` یا `npm`). کلید کش معمولاً از هش فایل‌های پیکربندی وابستگی (مانند `requirements.txt`) ساخته می‌شود. در صورت عدم تغییر این فایل، وابستگی‌ها مستقیماً از حافظه کش بازگردانده شده و زمان اجرای شغل به شدت کاهش می‌یابد.
* **آرتیفکت‌ها (Artifacts):** اشتراک‌گذاری فایل‌های خروجی (مانند فایل‌های باینری کامپایل‌شده، گزارش‌های تست یا وزن‌های مدل هوش مصنوعی آموزش‌دیده) بین شغل‌های مختلف یا ذخیره آن‌ها برای دانلود توسط کاربر پس از پایان فرآیند کاری.

### ۴. معماری امنیت و مدیریت دسترسی
طراحی امنیتی گیت‌هاب اکشنز بر سه اصل ایزوله‌سازی، احراز هویت کنترل‌شده و مدیریت اسرار (Secrets) استوار است:

* **توکن‌های موقت (`GITHUB_TOKEN`):** در ابتدای هر شغل، گیت‌هاب یک توکن امنیتی موقت تولید کرده و به اجراکننده می‌فرستد. این توکن پس از پایان شغل منقضی می‌شود و اختیارات آن (دسترسی خواندن/نوشتن به کد، بسته‌ها و غیره) قابل پیکربندی است.
* **مدیریت اسرار (Secrets Management):** اطلاعات حساس (مانند کلیدهای API، رمزهای عبور و کلیدهای دسترسی به ابر) به صورت کدگذاری‌شده در سطح مخزن یا سازمان ذخیره شده و فقط هنگام اجرا به صورت متغیرهای محیطی در اختیار اجراکننده قرار می‌گیرند. گیت‌هاب اکشنز به صورت خودکار مقدار این متغیرها را در خروجی لوگ‌ها ماسک (Mask) می‌کند.
* **اتصال به زیرساخت‌های ابری با OIDC:** برای اتصال امن به ابرهایی مانند AWS، GCP یا Azure بدون نیاز به ذخیره کلیدهای طولانی‌مدت، گیت‌هاب اکشنز از پروتکل OpenID Connect (OIDC) پشتیبانی می‌کند. در این روش، اجراکننده یک توکن JWT کوتاه‌مدت از گیت‌هاب دریافت کرده و آن را با نقش‌های امنیتی در ارائه‌دهنده ابر مبادله می‌کند.

## مثال عملی

در این بخش، یک فرآیند کاری جامع و واقعی را بررسی می‌کنیم. این فرآیند کاری برای یک پروژه هوش مصنوعی طراحی شده است که در آن ابتدا کدها در یک ساختار ماتریسی تست می‌شوند، سپس مدل هوش مصنوعی آموزش داده شده و در نهایت تصویر داکر (Docker Image) آن به مخزن بسته‌ها ارسال می‌شود.

### فایل پیکربندی فرآیند کاری (`.github/workflows/ai_pipeline.yml`)

```yaml
name: AI Model CI/CD Pipeline

on:
  push:
    branches: [ "main" ]
  pull_request:
    branches: [ "main" ]
  workflow_dispatch:

permissions:
  contents: read
  packages: write

jobs:
  # شغل اول: اجرا و تست موازی روی نسخه‌های مختلف پایتون
  test-and-lint:
    name: Test on Python ${{ matrix.python-version }}
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        python-version: ["3.9", "3.10", "3.11"]

    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}

      - name: Cache Pip Packages
        uses: actions/cache@v4
        with:
          path: ~/.cache/pip
          key: ${{ runner.os }}-pip-${{ hashFiles('requirements.txt') }}
          restore-keys: |
            ${{ runner.os }}-pip-

      - name: Install Dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt
          pip install pytest flake8

      - name: Lint with Flake8
        run: |
          # بررسی خطاهای سنتکس و فرمت کد
          flake8 . --count --select=E9,F63,F7,F82 --show-source --statistics

      - name: Run Unit Tests
        run: |
          pytest tests/

  # شغل دوم: آموزش مدل (وابسته به موفقیت شغل تست)
  train-model:
    name: Train AI Model
    needs: test-and-lint
    runs-on: self-hosted # استفاده از سرور اختصاصی دارای GPU
    
    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Install Requirements
        run: pip install -r requirements.txt

      - name: Run Model Training
        env:
          DATASET_URL: ${{ secrets.DATASET_URL }}
        run: |
          python scripts/train.py --output model.pt

      - name: Upload Model Artifact
        uses: actions/upload-artifact@v4
        with:
          name: trained-model
          path: model.pt
          retention-days: 7

  # شغل سوم: ساخت و انتشار تصویر داکر
  build-and-push-docker:
    name: Build & Push Docker Image
    needs: train-model
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'

    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Download Model Artifact
        uses: actions/download-artifact@v4
        with:
          name: trained-model

      - name: Log in to GitHub Container Registry (GHCR)
        uses: actions/docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build and Push Docker Image
        uses: actions/docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: |
            ghcr.io/${{ github.repository }}/ai-service:latest
            ghcr.io/${{ github.repository }}/ai-service:${{ github.sha }}
```

### تحلیل فنی خط به خط فرآیند کاری فوق

1. **تحریک فرآیند (`on`):** فرآیند کاری با ارسال کد به شاخه `main`، ساخت Pull Request، یا تحریک دستی (`workflow_dispatch`) فعال می‌شود.
2. **مجوزها (`permissions`):** به صورت شفاف دسترسی خواندن کد (`contents: read`) و دسترسی نوشتن به مخزن تصاویر داکر گیت‌هاب (`packages: write`) تنظیم شده است.
3. **شغل اول (`test-and-lint`):** 
   * از قابلیت `strategy.matrix` استفاده می‌کند تا فرآیند تست را همزمان روی ۳ نسخه پایتون اجرا کند.
   * کلید `fail-fast: false` تضمین می‌کند که اگر تست روی پایتون ۳.۹ شکست خورد، اجرای تست روی پایتون ۳.۱۰ و ۳.۱۱ متوقف نشود.
   * از اکشن `actions/cache` برای کش کردن پوشه `~/.cache/pip` استفاده شده است.
4. **شغل دوم (`train-model`):**
   * از کلید `needs: test-and-lint` استفاده کرده است؛ یعنی این شغل تنها زمانی آغاز می‌شود که تمام ۳ تست شغل قبلی با موفقیت پایان یافته باشند.
   * از `runs-on: self-hosted` استفاده می‌کند تا فرآیند سنگین آموزش مدل را روی سرور داخلیِ دارای کارت گرافیک اجرا کند.
   * فایل مدل تولید شده (`model.pt`) با اکشن `upload-artifact` ذخیره می‌شود.
5. **شغل سوم (`build-and-push-docker`):**
   * این شغل وابسته به شغل آموزش مدل است و با شرط `if` محدود شده تا فقط هنگام اجرا روی شاخه `main` (و نه بر روی Pull Request ها) اجرا شود.
   * فایل مدل از طریق `download-artifact` دریافت شده و به همراه کد در قالب یک تصویر داکر ساخته و به پایگاه داده تصاویری گیت‌هاب (`ghcr.io`) ارسال می‌شود.

## خطاهای رایج و نحوه رفع آن‌ها

توسعه و نگهداری فرآیندهای کاری اتوماسیون ممکن است با چالش‌ها و خطاهای مختلفی مواجه شود. در جدول و موارد زیر، شایع‌ترین مشکلات در گیت‌هاب اکشنز و راهکارهای حل آن‌ها به تفصیل بیان شده است.

| نوع خطا | علت اصلی | راهکار رفع خطا |
| :--- | :--- | :--- |
| **تخلف در دسترسی‌ها (Permission Denied)** | عدم تنظیم صحیح permissions یا انقضای توکن | تنظیم صریح کلید `permissions` در YAML یا بررسی دسترسی Secrets |
| **عدم تطابق اجراکننده (Runner Timeout / Stuck)** | نبود اجراکننده مناسب با برچسب‌های درخواست‌شده | بررسی آنلاین بودن Self-hosted Runner یا اصطلاح برچسب‌ها (`runs-on`) |
| **حلقه‌های بی‌نهایت (Infinite Loop)** | ارسال Commit توسط اکشن به همان شاخه‌ای که رویداد push دارد | استفاده از شرط‌های مناسب یا استثنا کردن کاربر ربات با `[skip ci]` |
| **تکمیل ظرفیت کش (Cache Size Exceeded)** | حجم کش از حد مجاز ۱۰ گیگابایت برای هر مخزن فراتر رفته است | بازبینی کلیدهای کش و حذف پوشه‌های زائد مانند فایل‌های لاگ |

### ۱. افشای اطلاعات حساس یا عدم ماسک‌شدن Secrets
اگر در اسکریپت‌های شل یا خروجی لوگ‌ها، متغیرهای حساس به صورت رشته‌های ترکیب‌شده (String Concatenation) چاپ شوند، ممکن است سیستم ماسک اتوماتیک گیت‌هاب نتواند آن را تشخیص دهد.

* **راهکار:** همیشه متغیرهای حساس را مستقیماً از طریق بخش `env` به گام‌ها تزریق کنید و از چاپ مستقیم آن‌ها در دستورات `echo` خودداری نمایید.

```yaml
# روش نادرست (احتمال افشای راز)
- run: echo "My secret is ${{ secrets.MY_SECRET }}"

# روش صحیح
- name: Use Secret safely
  env:
    MY_SECRET: ${{ secrets.MY_SECRET }}
  run: |
    python run_task.py
```

### ۲. بروز شرط مسابقه (Race Condition) در استقرارهای همزمان
اگر دو ارسال کد (Commit) با فاصله‌ای کوتاه انجام شوند، دو فرآیند کاری همزمان شروع به کار می‌کنند. این امر می‌تواند باعث شود فرآیند مربوط به کد قدیمی‌تر، بعد از فرآیند جدیدتر تمام شده و کد قدیمی روی محیط عملیاتی مستقر شود.

* **راهکار:** استفاده از قابلیت `concurrency` برای لغو خودکار اجراهای قدیمی‌تر.

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

### ۳. عدم پاک‌سازی محیط در اجراکننده‌های خود-میزبان (Self-hosted)
برخلاف اجراکننده‌های گیت‌هاب که پس از هر شغل نابود می‌شوند، اجراکننده‌های خود-میزبان حالت پایداری دارند. اگر فایل‌های تولیدشده در شغل قبلی پاک نشوند، ممکن است در اجرای شغل بعدی اختلال ایجاد کنند.

* **راهکار:** افزودن گام پاک‌سازی در انتهای شغل یا ابتدای آن با استفاده از اکشن‌های پاک‌سازی یا دستورات مستقیم شل:

```yaml
- name: Clean Workspace
  run: git clean -ffdx
```

## جمع‌بندی

پلتفرم گیت‌هاب اکشنز با ترکیب معماری رویدادمحور، ارکستراسیون توزیع‌شده و یکپارچگی عمیق با مخازن کد، استاندارد نوینی را در اتوماسیون توسعه نرم‌افزار و مهندسی سیستم‌های هوش مصنوعی ایجاد کرده است. 

همان‌طور که در این فصل بررسی شد، درک درست از تفکیک لایه‌های کنترل و اجرا، به‌کارگیری استراتژی‌های موازی‌سازی مانند اجرای ماتریسی، مدیریت بهینه منابع از طریق کش‌سازی و ایمن‌سازی فرآیندها با استفاده از OIDC و کنترل دسترسی‌ها، پایه‌های اصلی طراحی پکیج‌های اتوماسیون مقیاس‌پذیر هستند. 

استفاده از گیت‌هاب اکشنز نه تنها سرعت تحویل نرم‌افزار را افزایش می‌دهد، بلکه خطاهای انسانی در فرآیندهای پیچیده‌ای همچون تست، آموزش مدل و استقرار سیستم‌های توزیع‌شده را به حداقل می‌رساند. در فصل بعدی کتاب، به بررسی نحوه مدیریت و پایش این زیرساخت‌ها در محیط‌های عملیاتی واقعی خواهیم پرداخت.
